# 基于雷达实况和外推产品的强对流企业微信自动推送 — 实现方案说明

> 本文档说明该服务"做了什么、怎么判断、为什么这么判断"，供业务/评审/交接阅读。
> 技术部署见 `deploy/DEPLOY.md`，目录与快速上手见 `README.md`。

---

## 一、一句话概述

服务每分钟自动读取苏州雷达的**组合反射率实况**与**外推（临近预报）**产品，在苏州
市及市外 50 公里范围内自动识别强对流（强回波），结合未来 1 小时的外推推断其
**移动方向、影响到的区县/乡镇、强度等级、增强或减弱趋势**，在满足触发规则时
自动生成一段中文预警文本并附一张雷达实况图，推送到企业微信群。无强对流或
不满足触发条件时保持静默，不打扰群成员。

整个服务独立运行，不依赖也不影响其他系统。

---

## 二、数据来源

| 项目 | 说明 |
|------|------|
| 实况产品 Cr | 雷达组合反射率，单帧。文件名 `Mosaic{时间戳}_Cr.nc` |
| 实况产品 Et | 回波顶高（单位 **千米**），单帧，与 Cr 同时间戳、同网格。文件名 `Mosaic{时间戳}_Et.nc` |
| 外推产品 TreRef | 临近预报，单文件含 **21 帧**（当前 + 未来 2 小时，每 6 分钟一帧）。文件名 `Mosaic{时间戳}_TreRef.nc` |
| 获取方式 | 通过 SFTP 从雷达数据服务器远程读取，按日期目录 `{YYYYMMDD}/Cr|Et|TreRef/` 组织 |
| 网格 | 约 1000×1250 个格点，分辨率约 500 米 |
| 时间 | **文件名时间戳与产品时间均为 UTC（世界时）**，服务内部统一换算为北京时间显示 |
| 缺测约定 | `-32768` 表示超出雷达覆盖范围；`-128` 表示该点无回波；均按"无数据"处理 |

> 时间口径说明：经用真实样本文件交叉核对（文件名时间戳、产品生成时间戳 epoch、
> 外推帧时间 `tss` 三者一致），确认全部为 UTC。例如文件名 `…014800` 表示
> UTC 01:48，对应北京时间 09:48。外推第 1 帧时刻恰等于实况时刻，之后每帧 +6 分钟。

## 三、整体流程

```
每 60 秒循环一次：
  1. 找最新实况文件 Cr（按文件名时间戳取最新）
        若与上次已处理的相同 → 跳过本轮（避免重复）
  2. 读取实况网格（Cr 反射率 + Et 回波顶高），叠加地理掩膜
        （苏州市界 / 区县 / 乡镇 / 市外50km缓冲区）
        Et 文件缺失 → 本轮跳过（不推送），等待顶高数据落盘后下一轮再处理
        仅保留"顶高 ≥ 6km"的格点参与强回波判定（绘图仍用原始反射率）
  3. 在"市界+50km缓冲区"内检测强回波块（CR ≥ 35dBZ 且 顶高 ≥ 6km 同时满足）
        无强回波 → 本轮结束（静默）
  4. 读取同名外推 TreRef，取未来 1 小时（未来 10 帧）
        逐帧分析：移动方向 / 影响区县乡镇 / 强度极值 / 是否移入市内
  5. 判定回波来源（上游移入 还是 苏州局地生成）
  6. 去重判定（是否满足"该不该推"的触发规则）
        不满足 → 仅记录状态，不推送
  7. 满足 → 渲染雷达实况图 + 拼装预警文本 → 推送企业微信群 → 保存状态
```

## 四、关键判定逻辑（业务规则）

### 4.1 什么算"强回波块"

在检测范围（苏州市界 + 市外 50km 缓冲区）内，**反射率 ≥ 35 dBZ 且 回波顶高 ≥ 6 km
同时满足**的格点，做 **四连通**（上下左右相邻）连通域分析；连成一片且 **≥ 4 个格点**的，
才算一个有效"强回波块"。引入顶高约束可滤掉浅薄的层状云/虚假强回波，只关注深厚发展的强对流。

> 实现上：读取与 Cr 同时间戳的 Et（顶高，单位 km），把"顶高 < 6km 或顶高缺测"的格点
> 在参与判定的反射率副本中置为缺测，再走原有连通域/区县/触发逻辑；推送附图仍展示原始
> 反射率（不抹掉浅对流，便于人工研判）。若 Et 文件尚未就绪，则本轮不做判定、等待下一轮。

- 块强度 = 块内最大反射率。
- 强度等级 = 把强度向下取整到 5 dBZ 一档（37→35，42→40，46→45……），
  用于"等级是否上升"的去重判断。

### 4.2 外推分析（未来 1 小时）

对外推产品的未来 10 帧（约 60 分钟）逐帧分析：

| 输出 | 怎么得到 |
|------|----------|
| **移动方向** | **锁定"主威胁团"跨帧跟踪**：以首个有回波帧中威胁度最高的块为起点（威胁度＝距市界越近越高、同距下越强越高），之后每帧用最近邻匹配跟同一团（相邻帧质心跳变 > 约 30km 视为跨团，停止跟踪）；取该团轨迹首末位移归到八方位，位移过小（约 < 3km）记为"少动"。这样多回波并存时方向只反映同一个回波团，不会在不同团之间跳变 |
| **影响区县/乡镇** | 任意一帧中 ≥35dBZ 落入市内某乡镇多边形，即把该乡镇及所属区县计入影响集合（精确到乡镇） |
| **强度等级** | 各帧市内最大反射率取最大值，再取等级 |
| **增强/减弱趋势** | 外推市内最大反射率 vs 当前实况市内最大反射率：差 ≥ +5dBZ 记"增强"，≤ −5dBZ 记"减弱"，否则"维持" |
| **是否移入市内** | 未来任一帧市内出现强回波，则判定会影响本市；否则走"无明显影响"话术 |

### 4.3 回波来源判定

来源话术按**两个独立信号**判断，二者可**同时成立并在文案中并列同报**：

- **市外缓冲区**（市界外、50km 内）有强回波 → 报"上游"，并**精确定位**回波实际所在
  的上游地级市：统计缓冲区内各上游城市边界范围内的强回波格点数，按数量取命中城市
  （如"上海方向""无锡、常州方向"），不笼统罗列全部周边城市。
  - 上游城市边界来自 `data/upstream_cities.geojson`（由市级 shp 离线生成，带城市名，
    覆盖 无锡/常州/泰州/南通/上海/嘉兴/湖州）。
  - 若回波落在缓冲区但不属于任何已知上游城市（如海上），退回默认城市列表话术。
- **苏州市内**已有强回波 → 报"苏州的某些区县"（局地生成），点名具体区县。

三种组合的来源话术：

| 场景 | 文案"目前监测到在 X" 的 X |
|------|---------------------------|
| 仅市外缓冲区有 | "无锡、常州方向" |
| 仅市内有 | "苏州的吴中区" |
| 市外+市内同时有 | "无锡方向及苏州本地相城区"（**并列同报**） |

> 说明：旧版逻辑是"市内有则只报本地、不提上游"。现已改为两个信号独立判断、
> 可并列同报，避免"上游来袭 + 本地已生成"时遗漏上游信息。无论何种来源，
> 文案"将出现雷电活动"的受影响区县乡镇始终只统计**苏州市内**（实况 ∪ 外推入市，
> 精确到乡镇）；缓冲区市外的回波不写入受影响地名，仅参与触发判定。

### 4.4 推送触发与去重规则（核心：避免刷屏）

服务维护两类"轨迹"状态并持久化到磁盘（容器重启不丢，超过 30 分钟无强回波自动重置）：

- **接近轨迹（approach）**：缓冲区内、尚未明显入市的强回波。
- **区县轨迹**：苏州每个有强回波的区县各一条。

满足以下**任一**条件即触发一次推送：

| 触发条件 | 说明 |
|----------|------|
| 首次检测 | 某区县 / 缓冲区首次出现强回波，推一次 |
| 等级上升 | 实况强度每上升一个等级（+5dBZ），推一次 |
| 逼近里程碑 | 缓冲区回波距市界跨越 **25 / 10 / 5 km / 进入市内(0km)** 任一档，推一次 |
| 达到红色阈值 | 一旦 ≥ **45 dBZ**，之后每帧（6 分钟）持续推送 |
| 新区县出现 | 其他区县新出现强回波 → 单独开一条轨迹，规则同上 |

不满足任何条件时，即使有强回波也**抑制不推**，只更新状态。

## 五、推送内容

### 5.1 文本（两种话术）

**A. 会影响本市**（默认）：

> 【强对流天气提醒】目前监测到在{来源}有回波强度≥{等级}dBZ对流云团正在发展，
> 预计未来1小时回波将向{方向}方向移动，{增强/减弱/维持}，{受影响区县乡镇}将出现
> 雷电活动，并伴有短时强降水、雷雨大风等强对流天气，请注意防范！苏州市气象台{时间}发布。

**B. 对本市无明显影响**（缓冲区有回波但外推不入市）：

> 【强对流天气提醒】目前监测到在{来源}有回波强度≥{等级}dBZ对流云团正在发展，
> 预计未来1小时回波将向{方向}方向移动，{趋势}，移动路径对我市无明显影响。苏州市气象台{时间}发布。

### 5.2 附图

一张雷达组合反射率实况图（PNG），包含：标准 dBZ 配色色标、苏州市界（粗黑线）、
区县界（细黑线）、乡镇界（黑点线）、市外 50km 缓冲区（红虚线）、周边省市底图、
经纬度网格与标题时间（北京时间 CST）。

> 中文字体：绘图模块会从运行环境**实际已安装**的字体中挑选可用的中文字体
> （优先 文泉驿正黑 / Noto Sans CJK 等），容器镜像已内置 `fonts-wqy-zenhei`。
> 若环境无任何中文字体，图中中文会显示为方块，需先安装中文字体。

| 参数 | 默认 | 含义 |

| `REDALERT_DBZ` | 45 | 红色持续推送阈值 |
| `BUFFER_KM` | 50 | 市外缓冲区（检测范围）半径 |

| `LLM_BASE_URL` | — | OpenAI 兼容接口地址，如阿里云百炼 `…/compatible-mode/v1` |
| `LLM_API_KEY` | — | 接口密钥 |
| `LLM_MODEL` | — | 模型名，如 `qwen-plus` |
| `LLM_TIMEOUT_SEC` | 30 | 请求超时（秒），超时回退模板（云端模型建议 ≥30） |
| `LLM_TEMPERATURE` | 0.2 | 采样温度，低温减少发挥 |
| `LLM_ENABLE_THINKING` | false | 是否开启深度思考；qwen3 等混合推理模型关闭思考可显著降延迟，润色场景建议保持 false |

## 七、大模型文案润色（可选，默认关闭）

为让公众预警文案读起来更自然，服务支持一个**可选**的大模型（LLM）润色环节。
核心原则是 **数据由算法定死、模型只重组措辞**，因此即便接入大模型也不会带来"编造
数据"的风险：

- **算法是唯一数据来源**：仍由算法先生成权威模板文本（第五节话术），LLM 只在这段
  文本基础上调整语言风格，不参与任何判定或取数。
- **强约束提示词**：系统提示明确禁止新增/删除/修改任何数字、时间、方位、地名、单位，
  禁止编造降水量/风力级数等具体量值，禁止改变结论（是否影响本市、增强/减弱、来源方向）。
- **严格输出校验**（`app/llm_polish.py` 的 `_validate`）：
  - 模板中出现的所有数字 token 必须在润色结果中**全部保留**（按出现次数比对，丢失或
    改动数字即判不通过）；
  - 不得引入模板里没有的"带单位危险数值"（如 `50毫米`、`8级`、`30km/h` 等），防止
    模型凭空捏造量值；
  - 关键信息（发布时间字符串、受影响区县展示名、来源地名）必须原样保留；
  - 长度需在合理范围（过短或超过模板 2 倍即判不通过）。
- **模板兜底**：未启用、未配置完整、请求异常/超时、或上述任一校验不通过，都会
  **自动回退到算法生成的模板原文**。也就是说，开启 LLM 最多让文案更顺，绝不会让推送
  内容出错或延迟。

默认 `LLM_POLISH_ENABLED=false`（纯模板，零依赖零风险）；如需开启，配置上表中的
`LLM_*` 参数并填入 `LLM_API_KEY` 即可（接口为 OpenAI 兼容，默认指向阿里云百炼）。

## 八、当前简化与已知边界

- 实况叠加产品（≥20mm/h 短时强降水、≥7 级雷暴大风）暂未拼入文本（按需求约定）。
- 去重按"接近轨迹 + 各区县"建模，未对多个回波团做独立 ID 追踪。
- 上游/局地来源判定按"当前市内是否已有强回波"近似。
- 端到端时效中，"数据产出并落盘到服务器"的延迟由上游决定（实测约数分钟），
  服务一旦发现新文件，处理（读网格+检测+外推+绘图）通常在数秒内完成。

## 九、运行状态查看

- 健康检查：`curl http://<宿主IP>:8770/health`，关注 `webhook_configured`、
  `data_source`、`runtime.scans/pushes` 等字段。
- 实时日志：`docker logs -f radar-push`
  - 无强对流：周期打印 `no strong echo … in buffer`
  - 命中推送：打印 `PUSH at {时间} reasons=[…]` 及完整文本，并向群发送。
- 测试期若**不想推群**：`.env` 里把 `WECOM_WEBHOOK_URL` 留空即可，逻辑照跑、
  内容照打印在日志，但不会实际发送到企业微信。
